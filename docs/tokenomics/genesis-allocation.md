# Genesis Allocation

## Summary

The TIME Protocol genesis allocation should not be a founder allocation, investor allocation, or liquidity mining campaign.

It should be a human allocation.

Every verified human receives retroactive birthright TIME based on days lived.

## Genesis Principle

```text
Humanity is the genesis class.
```

## Problem With Conventional Token Launches

Most token networks launch with some combination of:

- founder tokens;
- investor allocations;
- foundation reserves;
- liquidity incentives;
- airdrops to existing crypto users;
- mining or staking rewards.

These methods privilege:

- capital;
- insiders;
- technical early adopters;
- existing token holders;
- geographic and internet access advantages.

TIME Protocol should invert this.

## TIME Genesis

TIME Genesis begins with the verified human.

```text
one verified human
one life lived
one retroactive birthright claim
```

## Allocation Formula

```text
genesis_TIME_for_human = days_since_birth × 1 TIME
```

## Why This Is Not an Airdrop

An airdrop rewards membership in a prior network or participation in a marketing campaign.

Retroactive Birthright TIME recognizes human existence and lived time.

This is not an airdrop.

It is a birthright.

## Initial Supply

The recognized genesis supply is the sum of all verified claims:

```text
recognized_genesis_supply = Σ(days_alive for each verified human)
```

The total does not need to be minted before claim.

Recommended model:

```text
claim-based recognition
```

TIME is recognized and minted as each verified human claims.

## Launch Mechanics

### Step 1: Verify humanity

A user proves they are a unique living human.

### Step 2: Prove age or days alive

A user provides a privacy-preserving proof of birth date or claim amount.

### Step 3: Calculate retroactive allocation

The protocol calculates days since birth.

### Step 4: Mint or recognize claim

The protocol mints or records the user's retroactive TIME.

### Step 5: Apply liquidity / vesting / governance rules

The protocol releases TIME according to the chosen launch model.

## Recommended Allocation Split

Example:

```text
20% liquid immediately
40% streams linearly over 10 years
40% immediately governance-allocatable but non-transferable
```

This is only a suggested launch policy.

The key principle is that every verified human receives meaningful starting currency and immediate political voice.

## Governance Use

Retroactive TIME should be usable for governance from day one, either directly or through a non-transferable governance allocation.

This avoids a situation where only buyers and employers shape the protocol.

## Economic Caution

A fully liquid retroactive allocation could create enormous sell pressure.

The solution is not to deny the birthright.

The solution is to distinguish:

- recognition;
- liquidity;
- governance power;
- transferability;
- vesting.

## Final Claim

> TIME Protocol does not launch with insiders. It launches with humanity.
